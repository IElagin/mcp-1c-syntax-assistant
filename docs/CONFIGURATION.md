# Конфигурация

Все настройки сервера — переменные окружения. Файл `.env.example` в корне
репозитория — образец: скопируйте его в `.env` и правьте копию.

Прежде чем править `.env`, прочитайте раздел
[«Как настройки попадают в контейнер»](#как-настройки-попадают-в-контейнер) —
он объясняет, почему при запуске через Docker правка `.env` ничего не меняет.

## Переменные окружения

Значения по умолчанию заданы в `src/core/config.py`; таблица повторяет их.

### Elasticsearch

| Переменная | Тип | По умолчанию | Назначение |
|---|---|---|---|
| `ELASTICSEARCH_HOST` | строка | `localhost` | Хост Elasticsearch. Внутри compose-контура — `elasticsearch`, имя сервиса. |
| `ELASTICSEARCH_PORT` | строка | `9200` | Порт Elasticsearch. Вместе с хостом собирается в URL `http://<host>:<port>`. |
| `ELASTICSEARCH_INDEX` | строка | `help1c_docs` | Имя индекса русской книги. Меняйте, если на одном кластере живёт несколько книг справки. |
| `ELASTICSEARCH_INDEX_EN` | строка | `help1c_docs_en` | Имя индекса английской книги — отдельный индекс, а не поле-фильтр в общем: в английской книге нет русских имён, склеивать нечего (см. [«Английская книга справки»](#английская-книга-справки)). |
| `ELASTICSEARCH_TIMEOUT` | целое | `30` | Таймаут одного запроса к Elasticsearch, секунды. |
| `ELASTICSEARCH_MAX_RETRIES` | целое | `3` | Сколько раз повторить запрос при обрыве связи или ответе 503/504. |
| `ELASTICSEARCH_RETRY_MIN_WAIT` | целое | `2` | Нижняя граница экспоненциальной паузы между повторами, секунды. |
| `ELASTICSEARCH_RETRY_MAX_WAIT` | целое | `30` | Верхняя граница той же паузы, секунды. |
| `ELASTICSEARCH_RETRY_MULTIPLIER` | целое | `1` | Множитель экспоненты повторов. |

Три переменных `ELASTICSEARCH_RETRY_*` в `.env.example` не перечислены, но
читаются: они управляют декоратором повторов в `src/core/retry.py`.

### Сервер

| Переменная | Тип | По умолчанию | Назначение |
|---|---|---|---|
| `SERVER_HOST` | строка | `0.0.0.0` | Интерфейс, который слушает сервер. Действует только при запуске `python src/main.py`; в контейнере адрес задан в `CMD` образа. |
| `SERVER_PORT` | целое | `8000` | Порт сервера. Та же оговорка. |
| `LOG_LEVEL` | строка | `INFO` | Уровень корневого логгера: `DEBUG`, `INFO`, `WARNING`, `ERROR`. |
| `DEBUG` | булево | `false` | `true` — простой текстовый формат логов в консоли вместо JSON. |
| `CORS_ALLOW_ORIGINS` | строка | `*` | Список источников через запятую; `*` — разрешить все. Учётные данные в CORS выключены всегда: аутентификации у сервера нет. |

Обработчик консоли жёстко настроен на `INFO`, поэтому `LOG_LEVEL=DEBUG`
добавляет отладочные записи только в файл `app.log`, а не в вывод контейнера.

### Данные

| Переменная | Тип | По умолчанию | Назначение |
|---|---|---|---|
| `HBK_DIRECTORY` | путь | `data/hbk` | Каталог, где сервер ищет русскую книгу справки. В контейнере смонтирован из `./data/hbk` только на чтение. |
| `HBK_FILENAME` | строка | `shcntx_ru.hbk` | Имя русской книги для индексации. В каталоге могут лежать и другие `.hbk`, поэтому выбор явный. |
| `HBK_DIRECTORY_EN` | путь | `data/hbk-en` | Каталог для необязательной английской книги. Отдельный от `HBK_DIRECTORY`, а не второй файл в том же каталоге: выбор книги для индексации и так задан именем, а раздельные каталоги делают состав очевидным на вид. В контейнере смонтирован из `./data/hbk-en` только на чтение — том уже объявлен в `docker-compose.yml`, добавлять его самостоятельно не нужно. |
| `HBK_FILENAME_EN` | строка | `shcntx_root.hbk` | Имя английской книги. См. [«Английская книга справки»](#английская-книга-справки), где её взять. |
| `LOGS_DIRECTORY` | путь | `data/logs` | Каталог для `app.log` и `errors.log`. Создаётся при старте, если его нет. В контейнере это `/app/data/logs`, туда же смонтирован `./data/logs` с хоста — см. [DEPLOYMENT.md](DEPLOYMENT.md#логи). |

### Язык ответа

| Переменная | Тип | По умолчанию | Назначение |
|---|---|---|---|
| `DEFAULT_HELP_LANG` | строка (`ru`/`en`) | `ru` | Язык ответа, когда инструмент вызван без параметра `lang` — тот же язык, который тогда попадает в схему инструмента как значение `default` (см. [MCP_TOOLS.md](MCP_TOOLS.md)). Проверяется на старте: сервер с опечаткой в значении не поднимется, а не отвечает молча не тем языком. |

### Индексация

| Переменная | Тип | По умолчанию | Назначение |
|---|---|---|---|
| `REINDEX_ON_STARTUP` | булево | `false` | `true` — переиндексировать при каждом запуске. `false` — индексировать только если индекс пуст. Действует на обе книги одинаково и независимо: у каждой свой индекс, и решение «нужна ли переиндексация» принимается для каждой отдельно (см. [«Английская книга справки»](#английская-книга-справки)). |

### Что переменными не управляется

Ограничение частоты запросов и размер пачки при индексации заданы константами в
`src/core/constants.py` — `REQUESTS_PER_MINUTE = 60`, `REQUESTS_PER_HOUR = 1000`
и `BATCH_SIZE = 100`. Переменных окружения для них нет.

Переменная `ELASTICSEARCH_URL` не действует: адрес всегда собирается из
`ELASTICSEARCH_HOST` и `ELASTICSEARCH_PORT`.

## Как настройки попадают в контейнер

Файл `.env` на контейнеры не влияет: `Dockerfile` его не копирует, `env_file` в
compose не подключён. Переменные для контейнера задаются в секции
`environment` файлов `docker-compose.yml` и `docker-compose.dev.yml`. `.env`
работает только при запуске сервера напрямую на хосте, без Docker — тогда его
читает `pydantic-settings`.

Без этого знания легко потерять час: правишь `.env`, перезапускаешь контейнер и
не понимаешь, почему ничего не изменилось.

Чтобы поменять настройку контейнера, добавьте её в `environment` нужного
сервиса:

```yaml
services:
  mcp-server:
    environment:
      - ELASTICSEARCH_HOST=elasticsearch
      - ELASTICSEARCH_PORT=9200
      - LOG_LEVEL=DEBUG
```

и примените изменение:

```powershell
docker compose up -d
```

Проверить, что именно видит контейнер:

```powershell
docker compose exec mcp-server printenv | Select-String 'ELASTICSEARCH|LOG_LEVEL|HBK|REINDEX'
```

## Переиндексация

Индекс строится один раз при первом старте. Переиндексация нужна, когда вы
заменили книгу справки или обновили парсер.

**Обновление до 2.4.0 требует переиндексации только ради пробелов после запятых
и двоеточий.** Описания вида «следующих действий:открытие панели ввода» теперь
читаются как текст; правка живёт в разобранном тексте, поэтому на уже собранном
индексе не видна. Остальные изменения версии — исходы индексации, параметр
`lang` у `/index/rebuild` и новые поля `/health` — переиндексации не требуют:
ничего из хранимого они не меняют.

**Обновление до 2.3.3 требует переиндексации, если статьи уже
проиндексированы.** Перевод строки внутри ячейки таблицы больше не теряется, и
примеры кода в статьях снова печатаются построчно. Текст статьи хранится в
индексе, поэтому на уже собранном индексе правка не видна: перестройте его
через `POST /index/rebuild`. Затронуты 32 статьи из 366 — у всех меняется
только разбивка на строки.

**Обновление до 2.3.1 требует переиндексации, если статьи уже проиндексированы.**
Правки этой версии живут в разборе статьи: текст сохраняет переносы строк,
заголовок не повторяется, подвал страницы и закомментированная разметка в него
не попадают, а точка внутри составного имени в примере кода остаётся на месте.
Всё это записано в индекс при разборе, поэтому на старом индексе не проявится.
Правка `get_1c_element`, наоборот, живёт в запросе и работает сразу.

**Обновление до 2.3.0 требует переиндексации, если вы кладёте книги статей.**
Статьи попадают в тот же индекс, что и карточки, и появляются только после
перестройки: на существующем индексе `get_1c_article` будет честно отвечать,
что статьи не проиндексированы. Если книги статей вам не нужны, переиндексация
не требуется — остальные три инструмента работают на прежнем индексе без
изменений.

**Обновление до 2.2.0 требует переиндексации обеих книг.** Правки этой версии
живут в разборе страницы, а не в запросе, и на старом индексе не проявятся:

- владелец глобальных процедур и функций записывается именем из книги
  («Глобальный контекст»), а не сегментом пути («Global context»), — иначе
  `list_1c_object_members(object="Глобальный контекст")` продолжит отдавать
  одни свойства без единого метода;
- `source_file` пишется в канонической форме (через `/`), от которой зависит
  склейка русской и английской книг при достройке английских имён.

Пока индекс не перестроен, сервер работает и отвечает — но этими двумя
улучшениями не пользуется.

Три способа, в порядке приоритета.

### 1. Флаг `--reindex` при запуске на хосте

```powershell
.\scripts\start_server.ps1 --reindex
```

```cmd
scripts\start_server.bat --reindex
```

Флаг разбирается в `src/main.py` и включает принудительную переиндексацию:
старый индекс удаляется, документы индексируются заново в фоне. Флаг имеет
приоритет над `REINDEX_ON_STARTUP`.

Через `uvicorn` флаг не пройдёт — скрипты запускают `python src/main.py`
именно поэтому.

### 2. Переменная `REINDEX_ON_STARTUP`

Для контейнера — в `docker-compose.yml`:

```yaml
services:
  mcp-server:
    environment:
      - REINDEX_ON_STARTUP=true
```

```powershell
docker compose up -d
```

Базовый compose — правильное место для такой настройки: он подхватывается
всегда. Значение из `docker-compose.dev.yml` голая команда `docker compose up
-d` не увидит — dev-файл нужно перечислять явно:

```powershell
docker compose -f docker-compose.yml -f docker-compose.dev.yml up -d
```

Автоматически подхватывался бы только `docker-compose.override.yml`, но такого
файла в проекте нет.

Для запуска на хосте — в `.env`:

```properties
REINDEX_ON_STARTUP=true
```

Верните значение в `false`, когда переиндексация закончится: иначе индекс будет
перестраиваться при каждом старте.

### 3. Эндпоинт `POST /index/rebuild`

Переиндексация работающего сервера, без перезапуска контейнеров. Параметр
`lang` выбирает книгу: `ru` (умолчание, прежнее поведение без параметра),
`en` или `both` — обе книги за один вызов. Так английский индекс
перестраивается по запросу, без `REINDEX_ON_STARTUP=true` и без перезапуска
контейнера.

```powershell
Invoke-RestMethod -Method Post -Uri http://localhost:8000/index/rebuild
```

```bash
curl -X POST http://localhost:8000/index/rebuild
```

Вызов синхронный: HTTP-запрос ждёт окончания индексации и может упереться в
таймаут клиента. Если ответа не дождались, проверяйте результат через
`GET /index/status`, а не повторяйте вызов вслепую.

Успешный ответ несёт исход на каждый запрошенный язык — «русский собран,
английской книги нет» — два факта, а не один статус:

```json
{
  "status": "success",
  "languages": {
    "ru": {
      "status": "success",
      "message": "Индексация завершена: документов 23491, из них статей 366.",
      "file": "data/hbk/shcntx_ru.hbk",
      "documents_count": 23491
    }
  }
}
```

Переиндексация только английской книги:

```powershell
Invoke-RestMethod -Method Post -Uri "http://localhost:8000/index/rebuild?lang=en"
```

```bash
curl -X POST "http://localhost:8000/index/rebuild?lang=en"
```

```json
{
  "status": "success",
  "languages": {
    "en": {
      "status": "success",
      "message": "Индексация завершена: документов 23471, из них статей 367.",
      "file": "data/hbk-en/shcntx_root.hbk",
      "documents_count": 23471
    }
  }
}
```

Неизвестное значение `lang` отклоняется с 422. Если ни одной из запрошенных
книг нет в каталоге — 400; если недоступен Elasticsearch — 503; если
переиндексация не удалась для всех запрошенных языков — 500, с тем же
объектом `languages` в `detail`, где у каждого языка свой исход. У 400 `detail`
две формы: строка с именем ненайденного файла, если книга была одна (`lang=ru`,
`lang=en`), и объект `{"languages": {...}}` с исходом на каждый язык, если книг
запрошено несколько (`lang=both`) и не нашлось ни одной.

### Как следить за ходом

```powershell
Invoke-RestMethod http://localhost:8000/index/status
```

До первого завершения индексации на этом сервере блок `indexing` несёт только
сырой прогресс, без исхода:

```json
{
  "elasticsearch_connected": true,
  "index_exists": true,
  "documents_count": 23491,
  "index_name": "help1c_docs",
  "indexing": {
    "is_active": false,
    "status": "idle",
    "progress_percent": 0.0,
    "total_documents": 0,
    "indexed_documents": 0,
    "start_time": null,
    "end_time": null,
    "error_message": null,
    "file_path": null,
    "outcome": null,
    "duration_seconds": null
  }
}
```

Как только фоновая индексация при старте сервера заканчивается, `outcome`
называет вид исхода (`indexed`, `parse_failed`, `nothing_to_index`,
`page_loss_too_high`, `index_write_failed` или `error`), а блок получает
`message` — тот же человекочитаемый текст, что видит и вызывающий
`POST /index/rebuild` в своём ответе. При успехе `error_message` остаётся
`null`; при отказе он дублирует `message`:

```json
{
  "elasticsearch_connected": true,
  "index_exists": true,
  "documents_count": 23491,
  "index_name": "help1c_docs",
  "indexing": {
    "is_active": false,
    "status": "completed",
    "progress_percent": 100.0,
    "total_documents": 23471,
    "indexed_documents": 23471,
    "start_time": "2026-08-13T14:25:13.321180",
    "end_time": "2026-08-13T14:26:06.338705",
    "error_message": null,
    "file_path": "data/hbk-en/shcntx_root.hbk",
    "outcome": "indexed",
    "duration_seconds": 53.02,
    "message": "Индексация завершена: документов 23471, из них статей 367."
  }
}
```

Этот блок отражает только фоновую индексацию при старте сервера — она одна
пишет в `indexing_manager`, который `/index/status` и читает. Ручной
`POST /index/rebuild` идёт другим путём: ответ синхронный и несёт исход
на каждый язык сам (см. выше), а `/index/status` после такого вызова не
меняется.

Индексация закончена, когда `is_active` равно `false`, а `documents_count`
перестал расти. Причина отказа читается из `message` (и дублируется в
`error_message`).

## Замена файла справки

Книга справки живёт в `data/hbk/` и в репозиторий не входит — `data/` внесён в
`.gitignore`. Файл проприетарный: копируйте его из своей лицензионной установки
1С:Предприятие (`C:\Program Files\1cv8\<версия>\bin\shcntx_ru.hbk`) и не
распространяйте.

Порядок замены:

```powershell
# 1. Положить новый файл под тем же именем
Copy-Item "C:\Program Files\1cv8\8.3.26.1234\bin\shcntx_ru.hbk" data\hbk\ -Force

# 2. Переиндексировать
Invoke-RestMethod -Method Post -Uri http://localhost:8000/index/rebuild

# 3. Убедиться, что число документов изменилось
Invoke-RestMethod http://localhost:8000/index/status
```

Каталог `data/hbk` смонтирован в контейнер только на чтение, поэтому новый файл
виден сразу — перезапускать контейнер не нужно.

Если файл называется иначе, задайте `HBK_FILENAME`. Индексируется ровно одна
книга: имя выбирается явно, а не по первому найденному `.hbk`, потому что в
каталоге могут лежать и другие книги — английская `shcntx_root.hbk`, справка по
языку запросов и прочие.

## Английская книга справки

Необязательна. Без неё сервер работает полностью на русском: имена элементов
и объектов при `lang="ru"` (умолчание) находятся и по-английски — см.
[README](../README.ru.md#поддержка-языков) — а `lang="en"` в этом случае
отвечает объяснённым отказом вместо карточки, а не пустым или обрезанным
ответом (точный текст — [MCP_TOOLS.md](MCP_TOOLS.md#кросс-языковые-запросы)).

Файл `shcntx_root.hbk` лежит в том же каталоге `bin` установленной
1С:Предприятие, что и `shcntx_ru.hbk`:

```
C:\Program Files\1cv8\<версия>\bin\shcntx_root.hbk
```

Порядок установки:

```powershell
# 1. Скопировать книгу в отдельный каталог
Copy-Item "C:\Program Files\1cv8\8.3.24.1234\bin\shcntx_root.hbk" data\hbk-en\

# 2. Проиндексировать книгу — без перезапуска контейнера
Invoke-RestMethod -Method Post -Uri "http://localhost:8000/index/rebuild?lang=en"

# 3. Проверить готовность
Invoke-RestMethod http://localhost:8000/health
```

Каталог `data/hbk-en` уже смонтирован в контейнер только на чтение — том
объявлен в `docker-compose.yml`, добавлять его самостоятельно не нужно.
Русская и английская книги индексируются при старте независимо друг от
друга: у каждой свой каталог, свой индекс и своё решение «нужна ли
(пере)индексация» (`src/infrastructure/indexing.py`, `auto_index_on_startup`).
Это касается только автоиндексации на старте: `POST /index/rebuild?lang=en`
перестраивает английский индекс по запросу в любой момент и не трогает
русский. Готовность видна в `/health` по полям
`index_en_exists`/`documents_count_en` — так же, как
`index_exists`/`documents_count` для русской.

### Переиндексация только английского индекса

`POST /index/rebuild?lang=en` переиндексирует только английский индекс — см.
[«Эндпоинт `POST /index/rebuild`»](#3-эндпоинт-post-indexrebuild) выше в этом
файле, там же формат ответа и `lang=both` для обеих книг разом.

### Достройка английских имён объектов

После (пере)индексации сервер ищет в английском индексе объекты и
конструкторы, у которых нет английского имени на собственной странице
русской книги, и дописывает найденное в соответствующий документ русского
индекса (`backfill_english_names`, `src/parsers/name_backfill.py`). Это
происходит один раз по итогам запуска или ручного `/index/rebuild`, а не при
каждом запросе, и результат остаётся в русском индексе даже после того, как
английский исчез: `list_1c_object_members(object="ValueTable", lang="ru")`
продолжит работать и без английской книги, а `lang="en"` — откажет с
объяснением, потому что это разные индексы и разная гарантия (см. раздел
[«Поддержка языков»](../README.ru.md#поддержка-языков) в README).

## Книги статей

Четыре книги статей — необязательные, как и английская книга карточек. Их
имена заданы одной таблицей `ARTICLE_BOOKS` в `src/core/constants.py`, а не
переменными окружения: эти имена файлов не отличаются между установками
1С:Предприятие.

| Ключ | Русский файл | Английский файл | Покрывает |
|---|---|---|---|
| `shlang` | `shlang_ru.hbk` | `shlang_root.hbk` | Встроенный язык |
| `shquery` | `shquery_ru.hbk` | `shquery_root.hbk` | Язык запросов |
| `shclang` | `shclang_ru.hbk` | `shclang_root.hbk` | Общий синтаксис |
| `dcsui` | `dcsui_ru.hbk` | `dcsui_root.hbk` | Выражения СКД |

Книги лежат в тех же каталогах, что и книги карточек — `HBK_DIRECTORY` для
русских, `HBK_DIRECTORY_EN` для английских (см. [«Данные»](#данные)) — и
индексируются вместе с ними в одном прогоне: `reindex_all` удаляет и
создаёт индекс заново, поэтому раздельная индексация карточек и статей
одного языка стёрла бы уже проиндексированные карточки. Прогон один и тот же
и при старте сервера, и по `POST /index/rebuild`: обе дороги ведут в
`index_hbk_file`.

Каждая книга не обязательна и не зависит от прочих трёх: отсутствие любой из
четырёх не мешает индексации остальных и книги карточек. Каких книг не
хватает, видно в `/health` — `missing_article_books` для русского каталога,
`missing_article_books_en` для английского.

Книга статей, которую не удалось прочитать, — не то же самое, что
отсутствующая: файл лежит на месте, но не открывается. `/health` называет её
через отдельные поля — `unreadable_article_books` для русского каталога,
`unreadable_article_books_en` для английского, — а не через
`missing_article_books`/`missing_article_books_en`: смысл разный, и ответ
разный. Отсутствующую книгу нужно положить в каталог; нечитаемую — заменить,
класть один и тот же битый файл на прежнее место бессмысленно. При индексации
разница стирается: что отсутствующей, что нечитаемой книги статьи не
индексируются, остальные книги и книга карточек — индексируются как обычно.
Файл книги, который не читается, не декодируется или не разбирается, теряет
только себя.

Книга карточек, потерявшая при разборе больше 5% страниц
(`MAX_TOLERATED_PAGE_LOSS_SHARE` в `src/core/constants.py`), переиндексацию
отклоняет — старый индекс остаётся как был, вместо того чтобы стать
наполовину пустым. Потерянной считается страница, не давшая документа:
не прочитанная, разобранная с ошибкой или разобранная в пустоту. Страницы,
отброшенные дедупликацией id (в английской книге таких 21), потерей не
считаются.

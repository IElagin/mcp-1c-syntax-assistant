# Устройство: решения и их причины

Здесь лежит то, что не выражается кодом, — почему выбран этот алгоритм, какой
дефект он закрывает и на каких данных это измерено. Замеры сделаны на книгах
8.3.20.1914: 23 125 страниц в русской, 23 104 в английской.

## Сквозной принцип: не отрицать того, чего не проверял

Пустой ответ неоднозначен сам по себе. «Ничего не найдено» одинаково звучит и
когда элемента нет в справке, и когда его нет у названного объекта, и когда
фильтр по виду отсёк единственное совпадение, и когда оборвалась связь с
Elasticsearch. Агент по такому ответу не может выбрать следующий шаг и обычно
выбирает неверный — прекращает поиск.

Поэтому каждая ветка пустоты называет себя отдельным значением `kind`, а сбой
Elasticsearch никогда не маскируется под «не найдено»: методы, чей пустой
результат является утверждением о справке (`object_exists`, `similar_objects`,
`_similar_members`), исключение не глушат — оно поднимается наверх и становится
честной ошибкой.

## Поиск

### Точечная запись «Объект.Элемент»

Разрез запроса проверяется по индексу, а не угадывается по синтаксису:
`SearchService._qualified_split` берёт первый разрез, чьё левое плечо
действительно является объектом справки.

Синтаксис здесь не решает. «ТаблицаЗначений.Добавить» и «Как добавить строку.
Пример кода» — одинаковый текст с точкой; различает их только справка. Прежнее
правило было чисто синтаксическим (одна точка, ни одного пробела) и отвергало
3 172 документа — 15,7 % всех точечных путей корпуса. Имена объектов справки
ему не подчиняются: они бывают с пробелами («Расширение формы клиентского
приложения для плана видов характеристик») и с точками внутри
(«WSСсылкаМенеджер.&lt;Имя WS-Ссылки&gt;» — таких объектов 220). Запрос
«Расширение формы клиентского приложения для плана видов
характеристик.РежимВыбора» уходил в семантический поиск и возвращал
ВидДекорацииФормы, ВидПоляФормы, ВидГруппыФормы — три чужих объекта.

Разрезы перебираются от самой длинной левой части к самой короткой: у
«WSСсылкаМенеджер.&lt;Имя WS-Ссылки&gt;.ПолучитьWSОпределения» объектом является
«WSСсылкаМенеджер.&lt;Имя WS-Ссылки&gt;», и разрез по первой точке дал бы
несуществующий объект. Все разрезы проверяются одной агрегацией: отдельный
запрос на каждую точку превратил бы поиск по длинному пути в пяток round-trip'ов.

Если ни одно плечо не опознано, применяется узкое синтаксическое правило. Оно
сохраняет фильтр по объекту, и `find_1c_help("ФоновыеЗадания.Выполнить")`
продолжает отвечать «объекта нет» вместо того, чтобы подсовывать одноимённые
элементы чужих объектов.

### Имя объекта: русское и английское

Фильтр по объекту принимает оба имени (`_object_filter`). Код 1С пишут
по-русски, а типы платформы часто узнают по английскому имени (`ValueTable`).
Английское имя заполнено у 22 821 документа из 23 125.

По той же причине оба имени матчит и подсказка о похожих объектах. Пока она
смотрела только в `name_ru`, русский ответ вёл себя так, будто английских имён
не бывает: `object="ТаблицаЗначенй"` давал «ТаблицаЗначений», а
`object="ValuTable"` — «подходящих не найдено». Отсутствие подсказки агент
читает как «объекта в справке нет» и прекращает поиск.

Ищет подсказка среди страниц объектов (`type="object"`), а не среди имён
элементов: `name_ru` элемента — это имя метода, и нечёткий поиск по нему находит
случайное совпадение корня в чужой фразе («Строка» входит в «Из строки» у
конструктора), после чего в подсказку попадает владелец найденного элемента,
не похожий на запрос ни по одной букве смысла.

### Порядок кандидатов при омонимии

69,1 % документов индекса имеют неуникальное имя: «Количество» встречается у
275 элементов, «Добавить» — у 197. Порядок: сначала настоящие типы языка, внутри
— объекты, у которых в справке больше элементов.

Ранжирование по релевантности здесь не работает: запрос фильтрующий, оценки у
всех совпадений равны. Прежний порядок был заявкой без покрытия — окно из 50
документов набиралось этим же фильтрующим запросом (то есть произвольно) и
сортировалось по алфавиту. Для «Количество» ответ начинался с
АгрегатыРегистраНакопления и ВсеЭлементыФормы, а ТаблицаЗначений, Массив и
Структура не показывались вовсе: агент делал вывод, что у обычных коллекций
«Количество» нет.

Число членов объекта — дешёвый и проверяемый признак: одна агрегация на все
объекты-владельцы сразу. Упорядочиваются все совпадения до потолка в 500
документов (самое многозначное имя корпуса — 275), а не окно выдачи; если имя
однажды перевалит за потолок, ответ скажет об этом (`full_order`).

«Настоящий тип» отличается от заголовка раздела справки по имени: под `object`
лежат и типы («ТаблицаЗначений»), и разделы вида «ОбъектМетаданных: Измерение»
— последние в коде не пишут.

### Поля и бусты

Буст по несуществующему полю — тихий ноль, а не ошибка, поэтому список полей
проверяется тестом (`test_queries_do_not_reference_removed_fields`).

- `syntax_all` заменило пару `syntax_ru`/`syntax_en`: второе было пусто у 100 %
  методов и всё равно участвовало в бустах.
- `parameters.name` и `parameters.description` убраны: плоский `match` по
  nested-полю не находит ничего — 0 попаданий против 11 у настоящего
  nested-запроса.
- Точное совпадение бустится по `name_ru.keyword`/`name_en.keyword`, а не по
  `name.keyword`: в последнем лежит слитное «Добавить (Add)», и буст не
  срабатывал никогда.
- `note` включён в семантический поиск осознанно: примечания справки несут
  оговорки, которые ищут словами («эффективно использовать для выборки
  неуникальных значений»).

## Состав объекта

Виды элементов перечислены явно (`MEMBER_KINDS`), потому что документ самого
объекта (`type="object"`) тоже несёт своё имя в поле `object`. Без фильтра
`members="all"` ловил и его: объект без единого метода получал `total=1` вместо
0, ветка «объект есть, но пуст» не срабатывала никогда, а у обычных объектов
счётчик был завышен на единицу.

Глобальные виды (`global_function`, `global_procedure`, `global_event`) входят
в состав наравне с объектными. Отдельный вид у них только по происхождению
страницы — справка держит их в `objects/Global context/`, — а принадлежат они
ровно одному объекту, глобальному контексту (510 документов из 510). Пока они
были исключены из фильтра, перечень глобального контекста показывал 87 свойств
и ни одного метода: ни `Сообщить`, ни `СтрШаблон`, ни `ЗначениеЗаполнено`
нельзя было перечислить ничем.

`total` — это число элементов в индексе, а не длина ответа. Пока здесь стояла
сумма вернувшихся списков, по ответу нельзя было понять, что `limit` срезал
хвост.

Конструкторы лежат отдельными страницами (`type="object_constructor"`, 389
документов у 307 объектов), а `variants` у всех 2 577 документов объектов пусты.
Карточка объекта читала эти пустые `variants` и печатала «Конструкторы: в
справке не указано» — про 307 объектов это была неправда, поэтому строки вызова
собираются отдельным запросом.

## Язык запроса и язык ответа

`lang` задаёт индекс, из которого приходит ответ, и язык самого ответа. Это
отдельная ось от того, на каком языке написано переданное имя.

Проверка «русское имя в английской книге» стоит на входе и только для значений,
которые ищутся точным совпадением: `name` у `get_1c_element`, `object` у всех
трёх инструментов. Для них она ничего не отрезает зря — ни одно поле
английского индекса не содержит ни одной кириллической буквы, значит exact-match
с кириллической строкой не найдёт там ничего ни при каких условиях.

Свободный `query` этой проверкой не режется. `multi_match` с `fuzziness`
матчит по отдельным токенам, и латинская часть смешанной строки находит
реальные совпадения: «Add (Добавить)» даёт 3 510 попаданий на живом индексе.
Поэтому кириллица в `query` становится объяснением только постфактум — когда
выдача и правда пуста.

Симметричной проверки для `lang="ru"` нет и не должно быть: русская книга несёт
оба имени в заголовке каждой страницы элемента, и `find_1c_help("Add",
lang="ru")` обязан продолжать находить элемент.

Проверка кириллицы идёт первой, отсутствие индекса — второй: первая не стоит
ничего, вторая — сетевой вызов. При обеих проблемах сразу порядок не влияет на
результат: кириллическое значение не найдётся в английском индексе, даже когда
он есть.

## Сборка ответа

Весь текст ответа собирается в `src/handlers/element_card.py`. Раньше рендер
был размазан по `mcp_formatter` и `search/formatter`, причём в первом жили два
одноимённых `format_quick_reference`, второй из которых перекрывал первый.
Состав объекта собирался вторым, независимым форматтером, привязанным к
удалённому полю `syntax_ru`: строки вызова не было ни у одного элемента, а у
конструкторов ответ сводился к голому «По умолчанию», из которого никак не
следует, что писать надо «Новый ТаблицаЗначений».

Ярлык строки вызова различается по виду элемента (`Вызов` / `Обращение` /
`Конструкторы`): по нему агент понимает, ставить ли скобки.

Английское имя в заголовок карточки не идёт — ни у метода, ни у объекта.
`full_path` и `object_ru` уже на языке ответа: при `lang="en"` в них лежит
английский текст, потому что документ пришёл из английского индекса.

«Описание варианта» печатается внутри варианта вызова, а не сливается с
описанием элемента: у метода с несколькими вариантами описания вариантов
разные, и склейка в одно поле стирает то, что относится не ко всем.

Параметры печатаются всегда, даже когда вариантов вызова нет: молчание
неотличимо от «данных нет».

Совет «перечень» печатается ровно тогда, когда под тем же ключом есть что
перечислять. У 100 страниц справки (параметры формы вроде «Расширение формы
клиентского приложения для документа.Ключ») заголовок разобран как объект, но
членов у него нет и само имя не встречается ни в одном поле `object` — совет по
нему отвечал «объект в справке не найден». Подставить вместо него родителя
нельзя: его методы принадлежат не этой странице, и выдать их за её состав
значило бы заменить тупик на неправду.

Совет «добрать остальное» называет достижимый предел, а не желаемый:
`find_1c_help` не примет `limit` больше `SEARCH_LIMIT_MAX`, и совет с
`limit=275` для «Количество» упирался бы в ошибку валидации схемы. Параметра
смещения у инструментов нет, поэтому повтор с бо́льшим лимитом возвращает те же
первые элементы, — формулировка говорит именно это.

Бюджет описания в строке списка — 140 знаков. Замер по индексу: медиана
описания 103 знака, медиана первой фразы 65; при прежнем пределе 100 обрезалось
51,3 % описаний.

## Разбор справки

### Владелец глобальных процедур и функций

Путь страницы английский в обеих книгах (`objects/Global context/methods/...`),
поэтому владельца глобальных может назвать только язык книги — имя берётся из
диалекта (`HelpDialect.global_context_name`).

Пока оно бралось из пути, один и тот же объект существовал в индексе под двумя
именами сразу: 510 процедур, функций и событий под английским «Global context» и
87 свойств под русским «Глобальный контекст» (свойства разбираются как обычные
члены и получают имя владельца из заголовка). Следствия:
`list_1c_object_members("Глобальный контекст")` отдавал 87 свойств без единого
метода, а `get_1c_element("Сообщить", object="Глобальный контекст")` отвечал,
что такого элемента нет.

Имя берётся из диалекта, а не из заголовка страницы: у 31 страницы из 510 в
заголовке стоит имя раздела книги («Процедуры и функции работы с XML»), и оно
завело бы десяток объектов-призраков вместо одного глобального контекста.

### Ключ склейки русской и английской книг

`source_file` записывается в канонической форме — через прямой слэш, как путь
и записан внутри самих книг.

Путь приходит из вывода `7z l` и потому зависит от платформы сборки: 7-Zip под
Windows печатает `objects\Global context.html`, p7zip под Linux —
`objects/Global context.html`. Само по себе это неважно, пока путь не становится
ключом, — а достройка английских имён склеивает индексы именно по нему.

На живом стенде русский индекс был собран на хосте, английский в контейнере:
term-склейка давала 0 совпадений из 23 104 возможных, и 653 документа остались
без английского имени, хотя парная английская страница была у каждого. Отказ был
молчаливым — достройка возвращала 0 и выглядела работающей: «кандидатов нет» и
«ключ не сходится» с её стороны неотличимы. Поэтому склейка вдобавок принимает
обе записи пути: индексатор канонизирует новые индексы, но уже собранные этим не
переписывает.

### Имя элемента и имя объекта в заголовке

Члены объекта берут имя владельца из `V8SH_title`, а не из собственного
заголовка страницы. У методов длинных объектов-расширений заголовок — просто
«Прочитать (Read)», без имени владельца; расщепление такого заголовка по точке
не находит точки и отдаёт его целиком, то есть в `object` попадает имя самого
метода. У соседнего объекта-расширения тоже есть метод «Прочитать», и оба
документа получали общий `id`, стирая друг друга при индексации.

Английская часть составного заголовка остаётся в имени и расщепляется
индексатором в `name_en`. Пока она отрезалась при разборе, поиск по `ValueTable`
не находил объект, хотя имя стоит в заголовке справки у 2 905 страниц объектов
из 3 063.

## Известные дефекты источника

У страницы `objects/catalog63/catalog343/GetFilesDialogParameters/ctors/ctor302`
английской книги в заголовке опечатка самой 1С: `GetFilesDialogParameters.By
title. directory choice and directory` — точка вместо запятой. Разбор по
последнему сегменту берёт хвост, и `name_en` этого конструктора равен
« directory choice and directory». Правило верно для остальных 23 103 страниц,
и подгонять его под одну опечатку источника дороже, чем она стоит.

Ещё две страницы английской книги не имеют заголовка вовсе — их имя пусто.

22 объекта доступны только по русскому имени: 21 такой страницы в английской
книге нет вовсе, а двадцать вторая озаглавлена там не именем, а внутренним
идентификатором страницы книги, — достройка такое значение не берёт.
